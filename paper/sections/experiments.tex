\section{Experiments}

All numbers in this section are synchronized from repository artifacts under
\path{reports/prestudy_5080/} and \path{results/prestudy_5080/}. The current
evidence should be read as an RTX 5080 prestudy for feasibility and mechanism
selection, not as the final full-scale benchmark.

\subsection{RTX 5080 Prestudy Protocol}

We keep the TTPI numerical configuration fixed and change only the action-mode
ordering. The formal HardMove runs use the state40/action50/iter30 setting with
seeds 0--9. The prestudy analyzes HM8 and HM12 standard environments, keeps OOM
runs as first-class outcomes, and records peak GPU memory, wall-clock time,
TT-Cross function-evaluation requests, per-iteration rank profiles, and
per-cut transient rank logs. HM16 at this configuration is not treated as a
5080 benchmark because all 150 formal HM16 runs in the current artifact set end
in OOM.

\subsection{Main Resource Comparison}

Table~\ref{tab:prestudy-5080-main} summarizes the existing HM8/HM12 formal
runs. In the text below, CouplingAwarePAM refers to the deterministic
block-preserving coupling-aware ordering implemented in the code as
\texttt{sensitivity\_pam}. On HM8, all listed orderings complete.
CouplingAwarePAM reaches the highest mean success rate (0.717) while keeping
memory and query burden close to BlockPAM. In contrast, the static
RankAwareProxy ordering has much larger memory (5012 MB) and query burden
(45.16M requests), despite running without OOM on HM8.

HM12 separates the methods more clearly. CouplingAwarePAM has the lowest OOM
count (1/10), the lowest mean peak memory among the completed/partial runs
(9477 MB), and the lowest mean TT-Cross request count (148.80M). Local and
BlockPAM have 3/10 and 4/10 OOM, respectively. The current HybridPAM is less
stable on HM12 with 7/10 OOM, and RankAwareProxy fails on every HM12 seed. The
safe conclusion is therefore not that a rank-aware proxy is solved, but that the
current deterministic coupling-aware block ordering is the strongest
candidate among the implemented variants.

\subsection{Why the Static Rank-Aware Proxy Fails}

The implemented RankAwareProxy objective is a static segmented cut-load
surrogate, not a dynamic singular-spectrum or TT-Cross rank estimator. The
prestudy supports this distinction empirically: on HM8 it increases both peak
memory and query requests, and on HM12 it produces 10/10 OOM runs. The
proxy--actual correlations in the current artifact set are weak or inconsistent
(for example, Pearson correlation with peak memory is \(-0.15\) on HM8 and
\(-0.01\) on HM12). This supports treating RankAwareProxy as a failure
mechanism ablation rather than as the main method. It does not show that
rank-aware ordering is impossible in principle; it shows that the current static
cumulative proxy is poorly aligned with the evolving bottleneck ranks observed
during TTPI.

\subsection{Coupling and Hybrid Ablations}

Because the current CouplingAwarePAM score is already a deterministic
angular-distance coupling proxy, we tested two empirical action-effect variants
only as prestudy candidates. Table~\ref{tab:prestudy-5080-lite} shows that both
are too expensive on HM8: FD5 roughly doubles the TT-Cross request count
relative to the current coupling-aware ordering, while the first-order variant
raises memory and rank even more. We therefore do not extend either lite variant
to HM12.

\subsection{Current Experimental Takeaway}

The current data support three conservative claims. First, action-mode ordering
substantially changes TTPI resource usage under fixed budgets. Second, the
implemented deterministic coupling-aware block ordering is the most
promising present main method. Third, static rank-aware cut proxies and naive
physics--sensitivity hybrids are not sufficient; they should be presented as
diagnostic ablations unless redesigned. The next full experiment should focus
on CouplingAwarePAM against Local, BlockPAM, BadSplit, and stress-test
environments, while reserving HM16 for a higher-memory server.
