\section{实验}

本节数字同步自仓库产物 \path{reports/prestudy_5080/} 与
\path{results/prestudy_5080/}。当前证据应解释为 RTX 5080 上的可行性与机制预实验，而不是最终全量 benchmark。

\subsection{RTX 5080 预实验协议}

实验固定 TTPI 数值配置，只改变动作模态排序。正式 HardMove 结果采用
state40/action50/iter30 配置和 seeds 0--9。预实验分析 HM8 与 HM12 标准环境，将
OOM 作为一类正式结果保留，并记录峰值 GPU 显存、运行时间、TT-Cross 函数求值请求数、逐迭代秩剖面和逐 cut 瞬时秩日志。当前配置下 HM16 不再作为 5080
上的正式 benchmark，因为现有产物中 150 条 HM16 formal 运行全部 OOM。

\subsection{主资源对比}

表~\ref{tab:prestudy-5080-main-zh} 汇总了已有 HM8/HM12 formal 运行。在 HM8
上，列出的排序均可完成。下文中的 CouplingAwarePAM 指代码中以
\texttt{sensitivity\_pam} 实现的确定性分块保留耦合感知排序。CouplingAwarePAM
的平均成功率最高（0.717），同时显存和 TT-Cross 查询负担接近 BlockPAM。相比之下，静态 RankAwareProxy 虽然在 HM8 不 OOM，但显存升至 5012 MB，查询请求达到 45.16M。

HM12 更清楚地区分了方法。CouplingAwarePAM 的 OOM 数最低（1/10），平均峰值显存最低（9477 MB），平均 TT-Cross 请求数最低（148.80M）。Local 与 BlockPAM
分别有 3/10 和 4/10 OOM。当前 HybridPAM 在 HM12 上不稳定，7/10 OOM；RankAwareProxy
在 HM12 的 10 个 seed 上全部 OOM。因此，安全结论不是“rank-aware proxy 已经解决”，而是当前确定性 coupling-aware block ordering 是已实现变体中最有希望的主方法候选。

\subsection{静态 Rank-Aware Proxy 的失败原因}

当前实现的 RankAwareProxy 是静态分段 cut-load 替代目标，而不是动态奇异谱或 TT-Cross 秩估计器。预实验经验上支持这一区分：在 HM8 上它提高显存和查询请求，在 HM12 上 10/10 OOM。当前产物中的 proxy--actual 相关性很弱或不一致，例如与峰值显存的 Pearson 相关在 HM8 为 \(-0.15\)，在 HM12 为 \(-0.01\)。因此，RankAwareProxy
应作为失败机制消融保留，而不是作为当前主方法。这并不说明 rank-aware ordering 在原则上不可行，而是说明当前静态累计 proxy 与 TTPI 过程中动态出现的瓶颈秩不匹配。

\subsection{Coupling 与 Hybrid 消融}

\subsection{当前实验结论}

当前数据支持三条保守结论。第一，固定预算下动作模态排序显著影响 TTPI 资源消耗。第二，当前确定性 coupling-aware block ordering 是最有希望的主方法。第三，静态 rank-aware cut proxy 和朴素 physics--sensitivity hybrid 都不充分；除非重新设计，否则应作为诊断消融呈现。下一轮正式实验应聚焦 CouplingAwarePAM 与 Local、BlockPAM、BadSplit 以及压力测试环境的对比，同时将 HM16 留给更高显存服务器。
